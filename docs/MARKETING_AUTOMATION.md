# 撮るだけ経理：広報・販促案の週次生成

`MARKETING_CHANGELOG.md` の前回成功時との差分から、日本語の広報案を生成します。
対象アカウントは **@TsumugiCapital**。すべて未承認の下書きです。Xへの送信処理、Xの認証情報、LPの自動更新は含みません。

## 実行とレビュー

1. この変更をデフォルトブランチへマージします。
2. GitHubの **Actions → Weekly marketing review pack → Run workflow** をデフォルトブランチで実行できます。以後は毎週月曜 **9:17（日本時間）** に生成します。GitHubの混雑により実行が遅れることがあります。
3. 実行結果の **Summary** で文案を読み、**Artifacts → marketing-review** をダウンロードします。
4. 実装状況・プラン条件・文字数・募集状況・開発者の経歴を確認し、採用する文案を編集してから手動で公開します。

外部AI APIキーもX APIキーも不要です。変更履歴の項目を用いたテンプレート生成なので追加のAI API費用は発生しません。GitHub Actionsの利用条件・保存容量はリポジトリ側の設定に従います。表現の多様性や自然な要約には編集が必要です。

公開リポジトリの成果物には機密情報を入れないでください。Actionsが無効なら有効化が必要です。公開リポジトリでは長期間活動がないとscheduleが無効になることがあるため、長期停止後はActions画面を確認してください。

## 保存されるもの

| ファイル | 内容 |
| --- | --- |
| `review.md` | ①共感投稿 ②新機能・変更のお知らせ ③15秒デモ台本 ④非エンジニア開発ストーリー ⑤β利用者募集 ⑥LP文案 ⑦FAQ候補、根拠リンク、確認項目 |
| `pack.json` | 上記の構造化データ、実装状況ごとの一覧、変更前後、保留理由、X文字数 |
| `changes.diff` | 変更履歴ファイルの前回からの差分。機能以外の変更も含む |
| `source.md` | 生成に使った変更履歴の原文 |
| `state.json` | 次回比較用のコミットSHAと原文SHA-256 |

成果物は最大90日保存（組織・リポジトリの上限設定に従います）。必要な案や承認記録は期限前に保管してください。ソースの履歴に広報成果物を自動コミットしません。PRとpushのチェックは別名 `marketing-preview` で14日保存し、週次処理の基準点には使用しません。

## 差分と実装状況の扱い

- 前回**成功した週次・手動実行**の成果物からコミットSHAを復元し、同じ変更履歴のGitオブジェクトと比較します。生成失敗・保存失敗・PRプレビューは基準点を進めません。
- 初回は全機能を棚卸しし、既存機能を「新機能」として告知しません。
- 同名機能の最新日付の記録を採用。日付の並び順には依存しません。同日同名の重複、不明な実装状況、解釈できない機能形式はエラーにします。
- 日付・行番号だけの変更を機能差分と数えず、追加・内容更新・実装状況の遷移・削除を区別します。改名は削除＋追加です。削除から「提供終了」を推測しません。
- 「実装済み」の必須項目が揃い、テスト状況に「本番稼働中」があり、未確定の表現がないものだけを機能紹介・デモに使用します。
- テスト中・構想を提供済みとして紹介しません。状態変更で実装済みになった場合も条件確認が必要です。
- 別の未提供機能名や英字のサービス名（例：freee）への言及がある実装済み項目も、提供範囲の混同を避けるため保留します。この機械判定は意味理解の代替ではなく、人による事実確認が必要です。
- 差分なしの週は新機能告知・LP/FAQの追加候補を見送り、実装済み機能から週ごとにテーマを選んで共感投稿・デモ・開発ストーリーを作ります。β募集は受付状況を要確認とします。
- LP/FAQだけの記述変更は、原文の反映指示と `changes.diff` に残します。LP文案は既存HTMLへの適用前に確認してください。
- Xの通常文字数と `twitter-text` による加重文字数（上限280）を表示します。ハッシュタグを含めて判定し、超過した案は「要短縮・投稿不可」とします。条件が消える機械的な切り詰めは行いません。最終編集後もXの投稿画面で確認してください。

### 導入時に確認した不一致

2026-09-22に確認した変更履歴ではfreeeはdry-runで検証中ですが、`index.html` のメタ説明・連携紹介・プラン・FAQにはfreeeが利用可能と読める記載があります。本処理は変更履歴を基準に保留し、LP自体は変更しません。実際に本番提供済みなら変更履歴に日付付きの正式な状態更新を追加し、検証中ならLPの表現を修正してください。

## 変更履歴の書式

既存の書式を維持してください。`###` の状態見出しは `実装済み` / `テスト中` / `構想` のいずれかです。最新情報は別日付へ同じ機能名で追記できます。新たな状態の記録には必要な項目をすべて記載し、古い項目の値を暗黙に引き継ぎません。

```markdown
## 2026-09-22

### 実装済み

- **機能名**：機能名
  - **変更内容**：利用者から見た動作。制限も明記。
  - **解決する利用者の悩み**：どの作業が負担だったか。
  - **利用者にとってのメリット**：確認できる改善内容。
  - **対象プラン**：対象プランと制限。
  - **操作方法**：実際の操作。
  - **テスト状況**：本番稼働中。確認内容。

### テスト中

- **機能名**：検証中の機能
  - **現在の状況**：プレビューのみ。本番提供はまだ行わない。

### 構想

- **機能名**：検討している機能
  - **現在の状況**：未着手。提供時期未定。
```

冒頭に参照されている `CLAUDE.md` はこの公開サイト用リポジトリにはありません。この運用手順を本処理の書式説明として使ってください。

## 基準点の復旧

前回成功した成果物が削除・失効した場合、勝手に初回へ戻さず失敗させます。履歴の書き換えで基準点が祖先でなくなった場合や、SHA・ハッシュが不正な場合も停止します。

以前の案と未処理の変更を確認したうえで、Run workflowの **reset_baseline** をチェックして実行すると、現状の棚卸しを新しい基準点にします。その回は新機能告知を作りません。失われた期間の変更を自動で復元する操作ではないため、その期間の告知は手動で確認してください。同じ実行を再実行した場合は最新成功時点との差分となり、既処理の変更は再告知しません。

## ローカル検証

Node.js 22以上を使用し、リポジトリのルートで実行します。

```sh
npm ci --prefix tools/marketing --ignore-scripts
npm test --prefix tools/marketing
node tools/marketing/generate.mjs
node tools/marketing/generate.mjs --previous-state marketing-output/state.json --out marketing-next
```

変更履歴は**コミット済みのHEAD**を読みます。未コミットの編集内容は入力に含めません。既定の出力先 `marketing-output/` と依存関係はGit管理外です。テストでは初回・差分なし・状態遷移・削除・書式異常・条件保持・X加重文字数・前回成果物の復旧判定を確認します。

## 将来の拡張

`pack.json` の `schema_version: 1` を外部連携の入口にします。`posts[]` に `id` / `account` / `text` / `weighted_length` / `hashtags` / `evidence` / `checks` / `review_status` / `approved: false` を出力し、全体の `mode` は `review_only` に固定しています。設定や環境変数で投稿を有効にするスイッチはありません。

X APIを追加する場合は生成処理とは別の承認・投稿処理を実装し、承認済みの最終本文のハッシュ、承認者・時刻、最新の提供状況、再計算した文字数、投稿済みIDによる重複防止を検証してから送信してください。認証情報はその処理にのみ渡します。現段階には送信実装・送信権限はありません。

自由なAI文案生成を追加する場合は `buildPack` の文案組み立て部分が拡張点です。状態判定・出典・文字数検証・未承認フラグと前回成功時の復旧処理を維持し、変更履歴の本文を命令として実行しないでください。

参考：[Xの文字数仕様](https://docs.x.com/fundamentals/counting-characters)、[GitHub Actionsの成果物](https://docs.github.com/en/actions/using-workflows/storing-workflow-data-as-artifacts)、[scheduleの仕様と制約](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。
